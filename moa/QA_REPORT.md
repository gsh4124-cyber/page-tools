## 이번에 반영한 개선

복구 메일 링크를 통한 비밀번호 변경, 모든 세션 로그아웃, 비밀번호 재확인과 확인 문구를 요구하는 모아 탈퇴, 중단된 첨부 삭제 재개, 명시적인 빈 계정 재시작을 구현했다. 탈퇴는 공유 Auth 계정을 지우지 않고 본인의 모아 문서·습관·첨부만 지운다. 비밀번호 변경은 공유 로그인 계정에도 적용됨을 화면에 설명한다.

실제 Auth 세션과 만료·차단 상태를 검사하며 탈퇴 후 이전 JWT와 재시작 이전 세션을 거부한다. 문서·예약 쓰기와 탈퇴는 같은 잠금을 사용하고, 잠금을 기다린 쓰기는 권한을 다시 검사한다. 공개 스키마 모아 함수는 SECURITY INVOKER이며 비노출 `moa_private`의 제한된 함수 4개만 SECURITY DEFINER다. RLS·FORCE RLS와 비공개 Storage를 유지했다. Storage 파일 작업은 API로 수행한다.

선택형 사진 최적화(최대 1920px WebP), 첨부·잔여 용량, 진행 상태, 최근 백업 시각, 오프라인 안내, 개인정보 없는 진단 파일, 현재 기기 모드 삭제, 별도 암호화 파일 복구 도구와 일회성 상태 검사를 추가했다. 현재 기기 삭제는 기존 v7 원본 데이터·다운로드한 백업까지 지우는 기능이 아니다. 저장 한도 48MiB/예약 96MiB를 늘리지 않았다. 자동 감시·알림 구독·오프라인 저장 대기열은 만들지 않았다.

## 이전 검증과 구분

이전 버전은 실제 48MiB 활성/96MiB 예약 한도·동시 예약·크기 허위 신고·참조 파일 보호·전체 복원 8개를 통과했다. 회원가입 메일 인증·실제 세션 갱신/폐기도 확인했다. 버전 2 배포 후에는 기능 6개와 정리 2개, 실제 헤더·로그인·PNG/WebM·자동 재생·백업·B 격리를 검사했다. 이 결과는 `qa-results.json`의 previousCheckpoint에 보존하며 이번 후보의 배포 후 검증으로 계산하지 않는다.

정적 호스팅에서 `_headers`가 적용되지 않아 Worker로 실제 응답 헤더를 보장한 기존 수정은 유지했다. 이번 Worker 후보에는 개인정보 없는 `/healthz`가 추가됐다. Storage 메타데이터 검증 트리거는 향후 Supabase Storage 업그레이드 후 회귀 검사가 필요하다. [Storage 스키마 지침](https://supabase.com/docs/guides/storage/schema/design). 삭제 후 캐시 사본을 피하는 기존 cacheControl/no-store 보완도 유지했다. [캐시 설명](https://supabase.com/kb/troubleshooting/storage-private-bucket-files-still-accessible-after-remove-access-or-logout).

기존 세 제품, 공통 tools, workflows의 diff는 0이며 main을 병합·push하지 않았다. 기존 초기 적용 전후의 컬럼·정책·버킷·원래 프로필 해시·Auth ID 일치는 이전 체크포인트로 보존한다. 이번 SQL은 모아 객체와 정확히 식별한 QA 계정만 변경했다. 원래 Auth/프로필 각각 1개를 재확인했다. 다른 제품의 실시간 카운터는 관찰 시각이 달라 동일하다고 주장하지 않는다.
